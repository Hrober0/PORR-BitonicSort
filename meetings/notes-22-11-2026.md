## Why two parallel versions?

The rules require the **same algorithm** to be parallelised with **two different tools** in Stage 1
(threads, processes or distributed arrays). We use one of each kind:

- **Processes** – separate Python processes, each with its own interpreter. The array lives in
  shared memory so every process sees it. Works on standard Python.
- **Threads** – many threads in one process sharing the array directly. Standard Python (with the GIL)
  runs only one thread at a time, so we **must use the free-threaded build (`python3.14t`)**.
  Otherwise threads give no speed-up.

Both versions use the same scheme (below) and the same functions from `common.py`.
Only the "how do workers run and synchronise" part differs.

## Algorithm (shared by everyone)

1. **Sequential (`seq.py`)** – iterative bitonic network on `array('d')`, n = 2^k:
   ```
   for k = 2, 4, ..., n:            # size of bitonic sequence
       for j = k/2, k/4, ..., 1:    # compare distance
           for i in 0..n-1:
               l = i ^ j
               if l > i: compare_exchange(a, i, l, ascending = (i & k) == 0)
   ```
2. **Parallel scheme (processes, threads, Kubernetes)** – p workers, p = 2^m:
   - split the array into p blocks of n/p elements,
   - each worker sorts its own block with `bitonic_sort_seq` (the same function as the sequential version),
   - then do log p · (log p + 1) / 2 **compare-split** steps. Worker `r` pairs with `r ^ (1 << j)`:
     one keeps the smaller half of the two blocks, the other keeps the larger half,
   - add a barrier (synchronisation) after every step.
3. **GPU** – one kernel launch per (k, j) step, one GPU thread per compare-exchange.

## Correctness checks (required by the rules)

- **Cauchy criterion:** after sorting, run one more bitonic merge pass and check that
  ‖x_new − x_old‖₂ = 0 (the result no longer changes).
- **Residual:** ‖x − sorted(x_copy)‖₂ = 0 (Euclidean norm), plus a check for no inversions.
- Checks are **not** included in the measured time.

## Measurements

- Pick n so the sequential version takes ~2 min. Pure Python gives roughly **n ≈ 2^22**,
  but calibrate this on the test machine.
- Sizes: n = 2^16, 2^18, 2^20, 2^22 (+ n_max). Workers: p = 1, 2, 4, 8 (16).
- Repeat each run 3–5× and take the median. Time only the sorting (no data generation or checks).
- Speed-up S(p) = T_seq / T_p, efficiency E(p) = S(p) / p. Show both in a table **and** on plots
  vs p, with a separate curve for each n.
- Run everything on **one machine** and record CPU model, cores and Python version.

**Aleksander – processes:**

**Michał – CUDA (Stage 2):**

  Without one, use OpenCL (`pyopencl`) or switch to `mpi4py` (message passing),

**Kuba – Kubernetes (Stage 2):**
- this fits the "cluster schedulers" category from the rules,
- simplest setup: the Kubernetes built into Docker Desktop (or `kind`/`minikube`) on one machine,
- one Docker image with `common.py` + `worker.py`; data blocks are stored as files on a shared volume (`hostPath`/PVC),
- `driver.py` (run locally) splits the data into p files, then starts a Kubernetes **Indexed Job** with p pods
  (each pod sorts its block via `JOB_COMPLETION_INDEX`),
- then for every compare-split step it starts a Job with p/2 pods (each pod merges one pair of block files) and waits until it finishes,
- expect a small speed-up because pod start-up is slow (seconds). That's fine – describe it in the report as communication/scheduling overhead.
